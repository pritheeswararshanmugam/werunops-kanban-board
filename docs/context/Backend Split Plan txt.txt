Data Persistence Issues
Current Problems:
1. Firebase Config Dependency
o Config hardcoded in firebase-config.js
o Cache clear ? Manual re-configuration required
o No environment variable support (static site)
2. No Backup Strategy
o Single Firebase project
o No automated exports
o No version history beyond Firebase retention
3. Data Retention Concerns
o Firebase free tier: 1GB storage, 10GB/month bandwidth
o No guaranteed 5+ year retention
o No compliance with data archival requirements
Recommended Solutions:
Option 1: Supabase (PostgreSQL + Realtime)
* 500MB database (free)
* Native auth with row-level security
* SQL queries for complex reporting
* Automatic backups
* 10-year retention compliant
Option 2: Firebase + Cloud Functions
* Scheduled exports to Google Cloud Storage
* Automated backups (daily/weekly)
* BigQuery integration for analytics
* Upgrade to paid plan for guarantees
Option 3: Hybrid (Firebase + GitHub)
* Firebase for real-time operations
* Daily export to GitHub repo (backup)
* Git history = version control
* Free unlimited storage

14. Lessons Learned
Technical Challenges
1. GitHub API is NOT a Database
o 422 errors on every save attempt
o SHA requirement creates race conditions
o Base64 encoding overhead
o Rate limits (5,000 requests/hour)
o Conclusion: Use proper database (Firebase/Supabase)
2. Static Site Limitations
o No server-side logic
o No environment variables
o Credentials exposure risk
o No backend validation
o Conclusion: Consider Netlify Functions or Vercel Edge
3. Real-Time Sync Complexity
o Conflict resolution needed
o Optimistic UI updates
o Offline queue management
o Network error handling
o Conclusion: Use battle-tested SDKs (Firebase, Supabase)
Development Best Practices
Do:
? Use Firebase/Supabase for real-time apps
? Implement proper authentication from day 1
? Test on actual mobile devices
? Set up error tracking (Sentry)
? Version control all changes
? Document API decisions
Don't:
? Use GitHub Contents API as database
? Hardcode credentials
? Skip input validation
? Assume desktop-only usage
? Use full-page reloads for sync
? Store passwords in plain text

20. Backend/Frontend Split Architecture Plan
Executive Summary
The WeRunOps application has reached a critical inflection point where architectural decisions will determine long-term viability. Current client-heavy monolithic SPA architecture creates fundamental limitations in security, analytics, and operational control. This document outlines comprehensive requirements for splitting into a proper 3-tier architecture.
Decision Rationale: Backend is mandatory, not optional. The current Firebase-only approach cannot deliver session analytics, proper authentication, or production-grade security without server-side infrastructure.

21.2 Why Frontend-Only Cannot Work
Technical Impossibilities:
1. Session Duration Calculation
o Requires: Server-side timestamp storage + delta calculation
o Client-only: Can be manipulated, lost on clear cache
o Verdict: Impossible client-only
2. Cross-Browser Presence
o Requires: WebSocket server or polling endpoint
o Client-only: Firebase presence system exists but requires backend for analytics
o Verdict: Partially possible, limited without backend
3. Login Hours Report
o Requires: SQL aggregation queries (SUM(duration), GROUP BY user)
o Client-only: Cannot run complex queries on Firebase JSON structure
o Verdict: Impossible client-only
4. Secure Credential Storage
o Requires: Server-side password hashing validation
o Client-only: Exposed in source code (current state)
o Verdict: Insecure without backend

23. Database Schema Design
23.1 Schema Requirements
Design Principles:
1. Normalization: 3NF for data integrity
2. Performance: Indexes on frequently queried columns
3. Security: RLS policies for multi-tenancy
4. Auditability: Timestamps on all tables
5. Scalability: Foreign keys with cascading rules
23.2 Core Tables
Users Table
CREATE TABLE users (
id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
username TEXT UNIQUE NOT NULL CHECK (char_length(username) >= 3),
password_hash TEXT NOT NULL, -- bcrypt or SHA256
email TEXT UNIQUE,
role TEXT DEFAULT 'user' CHECK (role IN ('admin', 'user')),
is_active BOOLEAN DEFAULT true,
created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
last_login TIMESTAMP WITH TIME ZONE
);
-- Indexes
CREATE INDEX idx_users_username ON users(username);
CREATE INDEX idx_users_active ON users(is_active) WHERE is_active = true;
-- RLS Policies
ALTER TABLE users ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Users can view own data" ON users FOR SELECT USING (auth.uid() = id);
CREATE POLICY "Admins can view all" ON users FOR SELECT USING (auth.jwt() ->> 'role' = 'admin');
Sessions Table (Core Requirement)
CREATE TABLE sessions (
id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
user_id UUID REFERENCES users(id) ON DELETE CASCADE,
login_time TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
logout_time TIMESTAMP WITH TIME ZONE,
duration_minutes INTEGER GENERATED ALWAYS AS (
CASE
WHEN logout_time IS NULL THEN NULL
ELSE EXTRACT(EPOCH FROM (logout_time - login_time))/60
END
) STORED,
ip_address INET,
user_agent TEXT,
browser TEXT,
location TEXT, -- City/Country from IP
session_token TEXT UNIQUE, -- JWT token reference
is_active BOOLEAN DEFAULT true
);
-- Indexes for analytics queries
CREATE INDEX idx_sessions_user_id ON sessions(user_id);
CREATE INDEX idx_sessions_login_time ON sessions(login_time DESC);
CREATE INDEX idx_sessions_active ON sessions(is_active) WHERE is_active = true;
-- Composite index for date range queries
CREATE INDEX idx_sessions_user_date ON sessions(user_id, login_time);
Tasks Table
CREATE TABLE tasks (
id SERIAL PRIMARY KEY,
client_id INTEGER REFERENCES clients(id) ON DELETE RESTRICT,
project TEXT NOT NULL,
task_name TEXT NOT NULL CHECK (char_length(task_name) >= 3),
staff TEXT NOT NULL, -- Future: REFERENCES users(username)
status TEXT NOT NULL CHECK (status IN (
'New', 'In Progress', 'Waiting Client',
'Waiting Supplier', 'Follow Up', 'Completed'
)),
priority TEXT NOT NULL CHECK (priority IN ('High', 'Medium', 'Low')),
start_date DATE,
due_date DATE NOT NULL,
waiting_for TEXT,
notes TEXT,
created_by UUID REFERENCES users(id),
created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
-- Indexes for filtering/sorting
CREATE INDEX idx_tasks_status ON tasks(status);
CREATE INDEX idx_tasks_staff ON tasks(staff);
CREATE INDEX idx_tasks_due_date ON tasks(due_date);
CREATE INDEX idx_tasks_client ON tasks(client_id);
-- Full-text search
CREATE INDEX idx_tasks_search ON tasks USING GIN(
to_tsvector('english', task_name || ' ' || COALESCE(notes, ''))
);
-- Auto-update timestamp trigger
CREATE OR REPLACE FUNCTION update_updated_at()
RETURNS TRIGGER AS BEGINNEW.updated_a t=NOW();RETURNNEW;END; LANGUAGE plpgsql;
CREATE TRIGGER tasks_updated_at
BEFORE UPDATE ON tasks
FOR EACH ROW
EXECUTE FUNCTION update_updated_at();

23.3 Analytics Views
Session Hours Summary (Pre-calculated)
CREATE MATERIALIZED VIEW user_session_summary AS
SELECT
u.username,
u.email,
COUNT(s.id) as total_sessions,
SUM(s.duration_minutes) as total_minutes,
AVG(s.duration_minutes) as avg_session_minutes,
MAX(s.login_time) as last_login,
MIN(s.login_time) as first_login
FROM users u
LEFT JOIN sessions s ON u.id = s.user_id AND s.logout_time IS NOT NULL
GROUP BY u.id, u.username, u.email;
-- Refresh strategy
CREATE INDEX ON user_session_summary(username);
REFRESH MATERIALIZED VIEW CONCURRENTLY user_session_summary;
Daily Activity Report
CREATE VIEW daily_activity AS
SELECT
DATE(login_time) as date,
user_id,
u.username,
COUNT(*) as sessions_count,
SUM(duration_minutes) as total_minutes,
ROUND(SUM(duration_minutes)/60.0, 2) as total_hours
FROM sessions s
JOIN users u ON s.user_id = u.id
WHERE logout_time IS NOT NULL
GROUP BY DATE(login_time), user_id, u.username
ORDER BY date DESC;

27. Security Implementation
27.1 Authentication Flow
Step-by-Step Process:
1. User Login (Frontend)
o Collect username/password
o POST to /api/auth/login
o Receive JWT token
2. Token Storage (Frontend)
o Store in localStorage.token
o Set expiry timestamp
o Include in all API requests
3. Token Verification (Backend)
o Extract from Authorization: Bearer <token> header
o Verify signature using JWT_SECRET
o Check expiry timestamp
o Return 401 if invalid
4. Session Tracking (Backend)
o On login: INSERT into sessions table
o On logout: UPDATE logout_time
o On token refresh: Extend session
27.2 Row-Level Security Policies
Users Table:
-- Users can only view their own data
CREATE POLICY "Users view own data" ON users
FOR SELECT
USING (auth.uid() = id);
-- Admins can view all users
CREATE POLICY "Admins view all" ON users
FOR SELECT
USING (auth.jwt() ->> 'role' = 'admin');
Tasks Table:
-- All authenticated users can view tasks
CREATE POLICY "Authenticated users view tasks" ON tasks
FOR SELECT
USING (auth.role() = 'authenticated');
-- Users can only edit tasks assigned to them or created by them
CREATE POLICY "Users edit own tasks" ON tasks
FOR UPDATE
USING (
staff = (SELECT username FROM users WHERE id = auth.uid())
OR created_by = auth.uid()
);
-- Only admins can delete tasks
CREATE POLICY "Admins delete tasks" ON tasks
FOR DELETE
USING (auth.jwt() ->> 'role' = 'admin');
Sessions Table:
-- Users can only view their own sessions
CREATE POLICY "Users view own sessions" ON sessions
FOR SELECT
USING (user_id = auth.uid());
-- Admins can view all sessions (for reports)
CREATE POLICY "Admins view all sessions" ON sessions
FOR SELECT
USING (auth.jwt() ->> 'role' = 'admin');
